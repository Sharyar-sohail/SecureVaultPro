## 5. Modular vault separation — the truth

Storage today (all verified):
- One Room database file, `VaultDatabase.kt:21-29`, six tables in it: `vault_entries`, `secure_notes`, `digital_cards`, `secure_contacts`, `totp_accounts`, `crypto_wallets`; files live outside Room in `filesDir` containers `.svf` with an encrypted index (`FileVaultRepository.kt:491-523`).
- Table separation is real; **key separation is not**. `CryptoManager.kt:331-373` — a single 32-byte DEK, wrapped once by the single Keystore alias `SecureVaultProMasterKey` (`:34`), encrypts every field of every table and every file container (`encrypt/encryptBytes/encryptFileBytes/encryptFileToStream` all call `dataKey()`).
- `WalletKeyVault.kt:7-10,67-95` and `BitgetCredentialVault.kt:11-24` state it in their own comments: wallet private keys and Bitget API secrets are sealed "through `BitgetSecretSealer` (on the device that is `CryptoManager`) … under the Keystore-wrapped data key". Same key.
- Cloud: one per-user vault key (`Keyring.kt:39-55`) seals **all seven** realtime modules — `RealtimeEngine.kt:315,366` take the single `keyring.deviceVaultKey()` for every module — and the same key, base64'd, seals the Drive envelope (`Keyring.kt:168-170`, `CloudSyncManager.kt:810`).
- Therefore: **a breach of one module exposes the others.** Anyone holding the DEK (rooted device + app-private prefs + Keystore access, or the owner's unlocked process memory) reads passwords, card numbers, notes, contacts, TOTP secrets, wallet private keys and file bytes together. Anyone holding the vault key + master passphrase opens every synced module. The only genuine isolation is (a) separate tables/RTDB segments — an attacker must still decrypt each one — and (b) the decoy session (`SessionManager.isDecoy()` guards at `VaultRepository.kt:274,283,291,295` and `Keyring.kt:240,451`), which keeps the vault key unpublished in decoy mode.
- `RealtimePaths` gives per-module subtrees under `data/<module>/<id>` (`RealtimeEngine.kt:264-265`) — that is path separation, not cryptographic separation — verified.
- Drive folders separate backup types (`GoogleDriveService.kt:62-63` appDataFolder vs visible archive folder), not security domains — verified.

Plainly: there is no per-module key scope anywhere in the codebase. The directive's "one breach does not expose others" is **not implemented**.
