# sync-probe — measuring the instant-sync delay

The acceptance bar for this project is a **push** from one frontend that the other frontend sees in
well under a second, *measured* rather than asserted. Three things here produce that number:

| file | what it is |
|---|---|
| `protocol.js` | the SVP-1 wire in plain Node: envelope format, PBKDF2/AES-256-GCM, the `{e,u,r,d}` node and the last-write-wins table |
| `client.js` | Realtime Database REST + the server-sent event stream (the push channel — nothing here polls) |
| `probe.js` | the latency measurement: two connections, one node, writes in both directions |
| `vector.js` | the cross-language known-answer vector → `sync_engine/contract/svp-contract-1.json` |
| `protocol.test.js` | 16 tests holding all of the above against the frozen contract |

## 1. Proof the two frontends run the same encryption (no token needed)

```
node tools/sync-probe/vector.js --check
node --test tools/sync-probe/protocol.test.js
./gradlew testDebugUnitTest --tests "*EncryptionContractVectorTest*" --offline
```

`svp-contract-1.json` is **generated by Node** (the maths the Blogger page runs) and **opened by the
JVM** (`KeyringCodec` + `KeyDerivation`, the maths the APK runs). Both must get the same plaintext
out of the same ciphertext. That is the check that the realtime sync rides the *old* encryption
untouched — change PBKDF2 iterations, the salt length, the IV length, the tag length or the envelope
shape on one side only, and one of these two runs goes red.

The file contains no key material: the two passphrases are public labels compiled into both sides,
and the keys appear only as sha256 fingerprints.

## 2. The network floor (no token needed)

```
node tools/sync-probe/probe.js --transport-floor --runs 5
```

The realtime rules reject every anonymous request, so this cannot measure a sync. It measures the
road one does travel: HTTPS round trip to `asia-southeast1`. Capture from
`sync_engine/logs/transport-floor-*.txt`.

## 3. The real push measurement (needs a signed-in token)

The database only lets a uid touch its own tree, so a push measurement needs that uid's Firebase id
token. Sign in on the web companion page, then in its console:

```js
window.SVP_TOKEN = await firebase.auth().currentUser.getIdToken();
window.SVP_UID   = firebase.auth().currentUser.uid;
```

and run it from a shell (the token is read from the environment only — never printed, logged or
written to the log file):

```
SVP_ID_TOKEN="<token>" node tools/sync-probe/probe.js --uid "<uid>" --runs 5 \
  --passphrase-env SVP_PASSPHRASE
```

What it does: opens **two independent connections**, each holding the database's change stream open
on `svp1/users/<uid>/probe`, then writes sealed `{e,u,r,d}` records from one and times how long the
*other* is told about it — five rounds phone-direction, five rounds web-direction, then the reverse.
It refuses to write anywhere except the caller's own tree, refuses `keyring|data|meta` outright, and
deletes the probe node afterwards unless `--keep`.

`--passphrase-env` additionally opens the account's real cloud keyring with this Node code and prints
only the key's sha256/12 fingerprint — the cross-frontend proof that the wrap the phone wrote is the
wrap the browser reads.

Output: per-round lines plus min/median/mean/p95/max per direction, saved to
`sync_engine/logs/sync-probe-<utc>.txt`. Exit code is non-zero if the median reaches 1000 ms or a
push fails to arrive within 20 s.

## 4. The measurement that happens by itself

Both frontends instrument their own traffic while in normal use, so real numbers accumulate without
running anything here:

- **APK** — appends every write/receive pair to `Downloads/SecureVaultSync.txt`
  (`SyncLatencyLog.kt`), including `tWrite`, `tAck`, `tReceive` and the delta `tReceive - u`.
- **Blogger page** — keeps `localStorage['svp-sync-log']` and shows the live delay in the on-page chip.

Those two files are the evidence for the "≥5 changes each direction" test: change data five times on
the phone, five times on the web, then read both logs.
