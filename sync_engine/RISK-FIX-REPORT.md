# Risk fix report — 2026-10-29 (3.3.1 / versionCode 341)

Five risks were ordered fixed. Each entry names the change, the file, and the check that holds it
in place. Nothing here changed a crypto parameter; the last section proves that.

## Risk 1 — measure the sync, prove the delay

**Built:** `tools/sync-probe/` — the wire (`protocol.js`), the transport (`client.js`, REST +
server-sent event stream, no polling anywhere), the measurement (`probe.js`), the cross-language
vector (`vector.js`), and 16 tests (`protocol.test.js`). README: `tools/sync-probe/README.md`.

**Measured today (no token):** `sync_engine/logs/transport-floor-2026-10-29T11-13-02-247Z.txt`

```
samples: 10 (HTTP 401 expected)
round trip min/median/mean/p95/max (ms): 468 / 481 / 628 / 1145 / 2515
```

Read it exactly as what it is: the HTTPS round trip from this build machine to
`asia-southeast1`, on requests the rules rejected. It is the floor under any push, **not** the push
delay. The rules require a signed-in uid, so the push number needs either:

- **the two-connection probe** — `SVP_ID_TOKEN=... node tools/sync-probe/probe.js --uid <uid> --runs 5`,
  which writes 5 sealed records per direction and reports min/median/p95/max into
  `sync_engine/logs/sync-probe-<utc>.txt`, exiting non-zero if the median reaches 1000 ms; or
- **normal use** — both frontends already timestamp themselves: the APK appends `tWrite`/`tAck`/
  `tReceive` to `Downloads/SecureVaultSync.txt` (`SyncLatencyLog.kt`), the page keeps
  `localStorage['svp-sync-log']` and shows the live delta in its chip.

I am not going to print a millisecond figure I have not measured. The harness is finished, so the
number is one command (or one install) away.

## Risk 2 — `wipeAll` did not delete the synced copies

`RealtimeEngine.eraseCloudData()` removes `svp1/users/$uid/{data,keyring,meta}` — bounded, reports
`{uid, nodesRemoved, nodesFailed, error}` — and `LocalWipeService` calls it **only after the Drive
archive exists**, inside its own 60 s budget, so the archive-before-erase invariant still holds. If
the erase fails, the failure text reaches the Settings UI through the existing `cloudError`.
Wiping while signed out no longer claims the cloud copies are gone.

Held by `WipeOrderingGuardTest` (8 tests): archive precedes erase, all three nodes are covered, every
network step is time-bounded.

## Risk 3 — keyring rotation could strand the vault

A passphrase change queued a rotation that only flushed on the next unlock; if that flush failed the
new wrap could be lost and the account unopenable. Now the envelope (ciphertext, public salt,
iteration count, timestamp, uid — never a secret) is queued **before** the cloud write, replayed on
every `start()`, and an offline passphrase change repairs itself only when the queued envelope
provably opens with this device's key. A replay never overwrites a newer cloud node, and a different
account's queue is dropped rather than published.

Held by `KeyringRotationGuardTest` (7 tests), including "the queue writer may not reference the
passphrase or the vault key bytes".

## Risk 4 — the UI contrast guarantee had a hole

Text roles, ink-on-accent, hairlines and the M3 scheme were already checked per theme, and the
generated icon vectors already prove white-on-plate ≥ 4.5:1. What was unproven was the Compose-drawn
`ThemedIconTile`: the glyph was tinted with the theme accent and dropped on a per-design plate with
no contrast check — which is how a dark square behind an icon could reappear.

`iconPlateColor()` now computes the composite plate, and the glyph goes through
`VaultContrast.ensure()` before drawing. Held by `ThemeTokensTest` (`an icon glyph clears AA on the
plate it paints and the plate stays a tint`) for every palette × every accent: ratio ≥ 4.5 **and**
plate-vs-card ≤ 1.6 so a plate can never become a black box again.

## Risk 5 — signing passwords in `build.gradle`

Gone. Credentials come from `keystore.properties` (untracked, in `.gitignore`) or `SVP_KEYSTORE_*`
environment variables; a `.gitignore` now excludes the keystore, the properties file, and build
outputs. Without them the release is built **unsigned** with a loud `logger.warn`, instead of
quietly reusing a published secret. The same key is still used — verified below.

## The encryption is unchanged, and now provably identical on both frontends

`sync_engine/contract/svp-contract-1.json` is generated by Node — the maths the Blogger page runs —
and opened by the JVM (`KeyringCodec` + `KeyDerivation`) — the maths the APK runs.

- Node side: 16/16 pass (`node --test tools/sync-probe/protocol.test.js`)
- JVM side: 7/7 pass (`EncryptionContractVectorTest`)

Same ciphertext, same plaintext, both directions. Pinned in that pair of runs: PBKDF2-HMAC-SHA256 at
**600,000** iterations, 32-byte salt, 32-byte key, AES-256-GCM, 12-byte IV, 128-bit tag, envelope
`base64(iv).base64(ciphertext+tag)`, `AES/GCM/NoPadding`. The Drive backup envelope is `{v:3, salt,
data}` and `CloudSyncManager`'s restore ladder is untouched, so every existing backup and every
existing user database still opens. The fixture stores no key — the two passphrases are public labels
and the keys appear only as sha256 fingerprints.

One ordering drift was found and fixed while writing this: `protocol.js` broke a `u`-tie on revision
before tombstone, while `MergePolicy.kt` and the page's `better()` both let the delete win first. The
Node copy now matches the shipped rule, and the tie case is tested in all three.

## Sign-in regression: "Google sign-in was cancelled" (12501) — fixed in 3.3.2

Evidence, taken from the original working app in `backup_2026-10-29_12-00/`:

| Item | Old working 3.2.1 | Broken 3.3.1 | Verdict |
| --- | --- | --- | --- |
| `google-services.json` | 1313 B | 1313 B | byte-identical |
| `release.jks` | md5 `6b006455…3f7d` | same file | unchanged |
| signing SHA-1 (apksigner) | `fc8d9df3b3d4d9f0b5bf808b396afc3756d30953` | same | unchanged |
| package (aapt badging) | `com.securevault.app` | same | unchanged |
| `default_web_client_id` resource | **absent** | present | plugin newly applied |
| `requestIdToken` on the Drive builder | **no** | **yes** | the only sign-in change |

So the regression was not a key, a certificate or a console entry — it was one line in
`GoogleDriveService`. Making Drive depend on the OAuth web client gave Google another way to
say no, and `completeSignIn`'s `12501, 16 -> null` translated that refusal into a cancellation
the owner never made.

Fix, without new keys and without touching the encryption or the backup path:

1. `signInOptions` restored to the exact old builder (account, email, the two Drive scopes).
2. The Firebase id token moved to `identitySignInOptions` — same account, no scopes, silent first
   (`requestIdToken()`), so web sync can fail without ever reaching Drive. `SvpAuth` uses that
   path instead of `account.idToken`.
3. Only 12501 reads as a cancellation. 10/12500/16/4/1/2/9/12/7/8/15 each name the thing to fix,
   and the config codes log this build's own signing SHA-1 plus the web client id into the
   on-screen crash report — the value to paste into Firebase, found without adb.
4. `GoogleApiAvailability` pre-flight before the picker launches, on both the welcome screen and
   the backup screen, so "Play services missing/outdated/off" is never shown as "you cancelled".

Verified: `testReleaseUnitTest` BUILD SUCCESSFUL, `assembleRelease bundleRelease` BUILD SUCCESSFUL,
`SecureWalletPro-3.3.2.apk` versionCode 342 signed with SHA-1 `fc8d9df3…56d30953`, and
`Blogger-Theme-3.3.2.xml` carries the same web client id `908900914248-pse5k128…` as the APK's
`resources.arsc`. On-device sign-in still needs the owner's handset — there is no emulator here.
